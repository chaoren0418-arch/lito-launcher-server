# SQL 寫入與記憶體規範

現行正式政策：**天堂角色資料唯讀，LiTo 只在戰鬥結算保存勝敗**。此政策固定於程式，不提供切換全面寫入的外控。

## 資料來源與權限

| 資料 | 來源 | LiTo 執行期權限 |
| --- | --- | --- |
| 物品、技能、NPC 基礎定義 | `380_db` | SELECT |
| 來源清單、GM 指令、戰鬥規則、出生點、NPC／目標、商店設定 | `380_lito` | SELECT |
| 帳號、角色、裝備、技能、寵物等 | 所選 `380_ac`／`380_ac_1`／`380_ac_2` 或自訂來源庫 | SELECT |
| 已資格化的原生資源與統一備註（10 表） | `380_lito.lito_resource_*` | SELECT；啟動時載入不可變快照，無戰鬥執行期寫入 |
| 結算收據（原生 0.6.60 起） | `380_lito.lito_battle_settlement` | SELECT；結算限定 INSERT／UPDATE |
| 累計勝敗及版本 | 所選來源庫 `character_lito` | SELECT；結算限定 INSERT／UPDATE |

SQL 管理者編輯 `lito_source_server` 或玩法設定屬管理操作，不是遊戲程序寫回。來源固定 ID 1～8，不能因停用某服而重新編號。只讀取天堂已保存的資料，無法看到另一程序尚未存檔的狀態。

## 管理權限

唯一來源為所選動態庫 `accounts.access_level`，沒有設定檔白名單。正數才具管理員身分；各 GM 指令另受 **LiTo 專用庫 `380_lito.commands.access_level`** 的最低等級約束。來源或帳號切換、登出／斷線清除權限快照；變更帳號 SQL 權限後重新登入。權限查詢只讀，不更改帳號等級。

`.item`、`.spawn`、`.de` 定義由 `database.lito.database` 指定的庫讀取，初始門檻皆為 200；不再讀取或回退至 `380_db.commands`。名稱不含句點，處理器分別為 `L1CreateItem`、`L1SpawnCmd`、`L1SpawnDe`，`system` 必須為 0。指令表每次執行查詢，修改門檻立即影響後續指令；刪除一列會停用該指令。新增名稱或處理器仍需實作伺服器接線，不會執行任意 Java 類別。

安裝 SQL 為 `db/lito_commands.sql`，需 SQL 管理者匯入；執行帳號只需該表 SELECT。既有安裝遷移保留三個同名指令的原門檻，缺少時補入預設，重跑不覆寫既有 LiTo 設定。不得把天堂整份 commands 匯入後宣稱全部指令可用。

## 玩家生命週期

1. 登入／選角：從所選來源載入帳號角色、裝備、技能與戰績，建立記憶體工作資料；帳號識別包含來源 ID。
2. 商店／戰鬥：金幣、物品數量、HP／MP、技能、冷卻與召喚物在記憶體運作。靜態模板仍可依需求 SELECT。
3. 結算：原生 0.6.60 經 `DurableBattleSettlement` 固定整場結果，先強制寫入本機待補存檔，再由 `SettlementSql` 保存收據、更新來源 `character_lito`。每個有效結果增加一勝或一敗；不回寫角色金幣、道具、技能或原始屬性。原有 SharedDatabase CAS 路徑保留供其他部署使用。
4. 清理：清除場次物件、NPC、區域效果、冷卻、特效期限、召喚物與攻擊者參照、未完成商店請求；移除商店物品。結算頁金幣歸零，回大廳補足 `native.tournament.allowance`。
5. 登出：清除帳號角色工作背包、寵物、倉庫、來源掛鉤及連線戰績版本快取。

排行所需的小型統計與已結算積分保留至伺服器生命週期結束，不能每場整批刪除。全服積分、月排行不保存至 SQL；累計勝敗可重載。結算後立即刷新大廳與排行，排行查詢本身不寫 SQL；原有上榜門檻與排序規則仍適用。

## 一致性與驗證界線

`character_lito` 支援 MyISAM／InnoDB。寫入使用單一 INSERT 或附版本、勝敗舊值條件的 UPDATE；衝突回報 CONFLICT，不覆蓋更新資料。MyISAM 不依賴 rollback；與「1-伺服器」共用的庫須遵守它對角色表引擎的要求，LiTo 不自行遷移。

原生 0.6.60 使用場次 UUID＋來源庫＋角色 ID 產生唯一收據。`character_lito.last_result_id` 與勝敗同一次寫入；SQL 回覆遺失後，重試會確認標記而不重複增加。收據表必須為 InnoDB，來源角色表不改引擎。正式安裝 SQL 見 `db/lito_battle_settlement.sql`。

待補存檔固定在本專案 `runtime/battle-settlements`，不是登入器可刪除的場次資料夾。SQL 異常每 2 秒重試，重啟先恢復已確定結果；成功後刪除待補存檔，只保留小型 SQL 收據。磁碟保存失敗時保留房間與待保存結果；不能把尚未落盤的結果當作已完成。已保存的勝負不因結算頁斷線改判；已釋放角色不因補存重新建立背包。

收據是持久化去重紀錄，不含物品或角色工作資料；暫不自動刪除，避免舊事件重播加計。未結束的比賽沒有可恢復勝負；本機磁碟及 MyISAM 硬體損毀不在此重試機制保證範圍內。故障測試使用獨立臨時資料庫並刪除，不得拿 MyISAM 玩家實表做「寫入後 rollback」測試。

回收採移除參照交由 JVM 處理，不強制 System.gc()。集合歸零不代表作業系統記憶體立即下降；既有 100 回合測試也不等於長時間壓力測試。

舊文件中的角色全面寫回、sidecar、城堡／租賃／完整 profile 持久化，是其他版本或候選設計，已封存且不適用此部署。新功能必須保留上述邊界；若要變更寫入範圍，需另外設計遷移與相容驗證。[驗證紀錄](VALIDATION.md)／[歷史](docs/HISTORY.md)。
