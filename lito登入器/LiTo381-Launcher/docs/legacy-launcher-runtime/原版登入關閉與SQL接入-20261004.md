## 結論與證據級別

本輪三份實際原版程序報告（memory 兩次、SQL provider 一次）都到達 `mode=2 / page=0 / protocol=0x0734FD33`，handler 為 key `0x00496200`、mouse `0x004962B0`、render `0x00495E40`。這與 2026-09-08 兩份保留的 native-manual 報告在實際登入前的採樣一致；歷史程序其後有有效帳密捕捉與來源／選角轉換，本輪沒有 C_LOGIN。因此尚未重現非 GUI 的 boot 狀態缺口，沒有根據這個停留狀態修改登入或關閉機制。

## 關閉路徑與 trace 限制

現行 Compat `WindowProc` 在收到 `WM_CLOSE` 後，才把 `lParam=1` 交給原版 WndProc `sub_47F340`。原版 case 16（`loc_47F455`）看 `byte_64BC04` 與 sentinel；符合時到 `loc_47FFD5` 設 `dword_62C9C4=1`、呼叫 `sub_4C65F0` 清 socket／Winsock，再交 `DefWindowProc`。`WM_DESTROY` 的原生流程包含 `PostQuitMessage` 參考呼叫 `0x0047F44B`。`sub_46B1A0` 是 Tournament 階段返回／離房命令，不能拿來代替整個程式的關閉。

另有一個必須與 WM_CLOSE 區分的來源條件：原版 `WM_SYSCOMMAND` case 274 在 `byte_64BBE8` 為真時可吞掉 `SC_CLOSE 0xF060` 等系統命令。這只證明「可能的前置分支」；本輪沒有採樣該旗標，也沒有收到 SC_CLOSE 的事件證據。Alt+F4 API 回傳後 tool 的後續請求回報 active request，且沒有 Compat forwarding-close log，所以不能把未收到 WM_CLOSE 誤判為產品拒絕退出。

`Start-LiTo381.ps1 -DetailedTrace` 同時加 `--trace-window-close` 與 `--trace-process-exit`；前者抑制 PostQuitMessage，後者在 WOW64 RtlExitUserProcess 暫停，限時後可記 `exit_intercepted_terminated`。transfer-stone producer 也可能自動加 process-exit trace。本輪三次 native run 均未使用這些抑制退出旗標；180／180／40 秒限時結果仍是 `timeout_terminated / 0xC0DE0001`，不是自然退出或 crash。

歷史 `LiTo-close-native.json` 曾記 `exited / 0x00000000`，但屬 automatic 診斷；9/8 native-manual 報告記 `exited / 0x0019FFCC`。它們只作保留來源對照，不列為本輪退出通過，更不把非零值默認為 clean exit。驗收必須記 raw status／exit code、實際 close 或 credits 事件及清理，而不是只有 UI 消失。

## 工具恢復後／人工操作的最小入口

1. 取得當時 ready 的 provider 契約與由提供者指定的 **玩家** 測試帳號；MySQL 的 `credential_settings` 不是玩家帳密，不混用，也不抄到取證文件。重建自己的 config mapping、跑正式預檢，核對精確 BIN／JAR、數值 schema 4、LOGIN／GAME owner。使用通過驗證的 client-only launch plan，人工完整流程將 TimeoutSeconds 設為 0；不開 DetailedTrace、不啟動同端點 Server。
2. 確認當前原生帳密頁真的可見並取得焦點，再實體輸入與按登入／Confirm。預期 `C_LOGIN 01 → S_LOGIN_CHECK 00 → S_SERVER_LIST 3B`；取證只記方向／opcode／結果，遮蔽帳密。不見 C_LOGIN 時，先區分表單驗證／focus／callback，不直接推論 Server auth 失敗。
3. 在原生來源 modal 選交接列出的來源，預期 `C_C8 → S_F4` 的 GAME handoff，再有第二段 `S_KEY → C_VERSION → accepted → C_LOGIN`、`S_E6 → C_E2`、角色數／目錄 `S_03/S_CB`。選角色 Confirm 才送 `C_C9`；選頻道才送 `C_CA → S_C9/S_CA → C_CE → S_CC`。這是 9/8 保留 capture 的手動分支；早期 cached C35／自動角色文檔不能當成本輪實測。
4. 本輪要確認 game 完整操作時，至少記一個原生房間的 `C_CC/C_CF → S_CE/S_CD`、分隊 `C_D3`、參與者準備 payload 或房主開始的 `C_D2`、`S_E1 3/2/1 → S_WORLD → S_D2/S_E2`，再有實體 `C_MOVE/attack/skill`、結算、來源限定 SQL before/after。其他模式／地圖仍分開標示測試與 GUI 證據，不用一個畫面宣稱全部。
5. 自然退出分兩個入口驗：標題列 X 的 WM_CLOSE／native forwarding 與實際退出；大廳原生「離開」的 `C_QUIT 0F → credits → 原生關閉`。同時記實際 process status／raw exit code、socket／資源還原。不能把房間 `C_D0` 返回、timeout、trace 截留或強制關閉 owner 視為自然退出。

## 供 Modern 參考的邊界

Modern 可參考上述原生階段、來源→角色→頻道的操作順序、mode id／資源對照與封包證據級別；原生位址、callback pointer、640×480 widget 內部座標只適用此 BIN，不能作 Modern 執行 API。Modern 的帳戶認證、回合資料與寫入以 Server 的來源限定 `(source_server_id, char_obj_id)`、runtime 完整數值及來源權威契約為準；不要從原生安全影子欄位還原真實素質，也不要把本輪握手或歷史 GUI 檔當成 Modern／新原版流程已通過。
